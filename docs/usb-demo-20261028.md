# Veritxt USB defense demo

The `usbDemo` development build receives fictional messages from an authorized ADB laptop and automatically uses the installed model to post the existing initial SMS report. No **Check** tap, internet access, SIM, cellular reception, SMS permission, or incoming-SMS setting is required. Every demo report is labeled **Demo**, including the group header when all its reports are demo messages. Expand a notification to see the risk score, model category, and analysis; **View report** opens that message and checks it through the normal result screen.

The app installs separately as **Veritxt · USB Demo**, package `ph.smishguard.demo.usb`, Android 8/API 26 or newer, version `0.3.0-usb-demo`. It includes the frozen Ham/Smishing Linear SVM and raw-SMS adapter from the current Ham/Smishing build, with the current `linked-cashback-claim-deadline-v1` risk policy. There is no retraining or model substitution. The model category and the app's evidence-based risk score remain distinct: the risk score is not a probability.

## Before the defense

1. Extract the demo kit to the laptop. Install Android SDK Platform-Tools (`adb`) and any phone USB driver in advance; put `adb` on PATH. These preparations may need internet, but running the installed kit does not.
2. On the phone enable Developer options → USB debugging. Connect with a USB data cable and approve this laptop's debugging prompt. `adb devices` should show the phone as `device`, rather than `unauthorized`.
3. In PowerShell, open the extracted kit directory and run:

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File .\usb-demo.ps1 -Install
   ```

4. In **Veritxt · USB Demo**, accept the privacy notice and finish onboarding. Incoming SMS may stay **off** and SMS permission may stay **denied**. The install command grants Android notification permission on Android 13+; ensure both the normal-report and warning channels are enabled in Android settings.
5. Rehearse with the phone unlocked, airplane mode on, Wi-Fi off, and mobile data off. Leave the cable connected. The script does not change radios or enable SMS scanning. Use the notification shade if Do Not Disturb or the phone's settings suppress heads-up banners.

If multiple devices are connected, add `-Serial YOUR_DEVICE_SERIAL` to each script command. Run `adb devices` to find it. No physical phone was connected during development verification; rehearse on the defense phone before the event.

## Run the presentation

Run the five fictional samples, four seconds apart:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\usb-demo.ps1
```

Send a single fictional message:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\usb-demo.ps1 -Message 'Fictional test: Send your OTP immediately.'
```

Use a JSON file with your own fictional `id` and `text` pairs:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\usb-demo.ps1 -CasesPath .\my-fictional-messages.json -DelaySeconds 6
```

The included JSON contains inputs only. Neither the receiver nor script accepts a requested classification or risk score. Actual outputs are computed on the phone and may abstain. In API 36 verification, the included samples produced:

| Sample ID | Observed notification | Observed model category |
|---|---|---|
| `meeting` | Low Risk, 0/100 | Ham |
| `fictional-promotion` | Medium Risk, 40/100 | Smishing |
| `fictional-credential-request` | High Risk, 100/100 | Smishing |
| `insufficient-words` | Unable to assess, no score | No classification |
| `number-only` | Unable to assess, no score | No classification |

The unknown-word sample exercises actual model abstention. A number-only input exercises the existing app input-scope guard; the SMS classifier does not claim to identify a phone number. Missing, invalid, failed, busy, or timed-out inference uses the existing unscored fallback instead of a fabricated result. Failure fixtures exist only in the separate test APK, which is not included in the kit.

## Fit with the existing flow

`UsbDemoReceiver` validates a bounded Base64/UTF-8 payload, then calls `IncomingSmsNotifications.show(..., demo = true)`. That uses the same `SmishGuardApp.assess`, installed detector, risk policy, five-second inference deadline and busy retry, `InitialSmsReport`, `CheckPrompt`, risk gauge, opaque notification actions, and in-memory pending-message store as normal incoming reports. Privacy acceptance and notification permission are checked before and after inference. Explicit USB invocation replaces the normal telephony/SMS/scanning-consent gates for demo input only.

The ADB command uses an explicit component and action:

```text
adb shell am broadcast --include-stopped-packages -n ph.smishguard.demo.usb/ph.smishguard.demo.UsbDemoReceiver -a ph.smishguard.action.USB_DEMO_MESSAGE --es message_base64 BASE64_OF_UTF8_FICTIONAL_MESSAGE
```

The script handles encoding, device selection, result checking, Unicode, newlines, and shell punctuation. A successful ordered broadcast returns `result=-1` and `Demo report posted`; invalid payloads return 2, privacy/notification gates return 3, and receiver-level processing errors return 4. Only fictional inputs belong on this developer transport: ADB/Android tools can observe its submitted payload. Pending messages remain in app process memory, expire after ten minutes, and disappear when opened or dismissed. As with existing reports, Android notification history may retain previews if the phone owner enabled that feature.

## Build boundary and verification

The receiver class and manifest registration exist only under `src/usbDemo`. Its exported receiver requires `android.permission.DUMP`, which ADB shell has and ordinary apps do not. It also checks `BuildConfig.DEBUG` and `USB_DEMO_ENABLED`; the latter is false for every other build type. The separate release APK was assembled and checked for absence of the receiver in both its manifest and DEX. Demo notifications and their title marker are confined to explicitly requested demo reports.

Model SHA-256: `15cc0105b0e51e5342682ea36896c4436e515c39d165faf040476046b6b8059c`.

Raw-SMS adapter SHA-256: `11c3ee93fb7523e72b5658bec9f4bc5ee7389d9e5add25d5ca3fceceeedb5b8c`.

Build and reproduce from the private workspace:

```powershell
.\scripts\build_usb_demo.ps1 -TestApk
python .\scripts\verify_usb_demo.py --output output/usb-demo-new-verification
```

The verifier accepts only a booted emulator, temporarily disables its radios, and restores their prior settings. The delivery's `verification.json`, `build-verification.json`, and logs record the exact APK identity and checks. API 36 checks cover the delivered PowerShell transport, six real-model notification/open-result pairs (including a Unicode/shell-literal sample), 515 frozen model fixtures and 33 raw-SMS fixtures, privacy and failure fallbacks, 16 existing notification checks, malformed broadcasts, and a normal app cold-start notification after force-stop without instrumentation or a Check tap. JVM and lint results, release exclusion, and APK signature validation are recorded alongside these checks. No physical-phone verification is claimed.

The final kit was exercised with Windows PowerShell 5.1. Build validation passed 50 demo JVM tests and 48 release JVM tests, with 16 conditional skips per variant and no failures or errors. Lint reported zero errors and 17 warnings. The Android run passed 19 checks, including its setup check for a separate normal-process cold start. The model and adapter parity checks are additional fixture counts, not accuracy measurements.
